# 服务端需求:账号自身信息(wechat_accounts)

> 提出方:采集端(wechatauto-replica)。实施方:`aizee_soup/aizee-crm/aizee-wechat`。
> 采集端已按本文契约实现并可上线,服务端未部署时自动降级(见 §5),不阻塞现有同步。

## 1. 背景与问题

现有六张表全部以 `account`(= `wxid_xxx`)作为关联键,这本身没问题。但 **`account`
只是一个关联键,不含任何身份信息** —— 服务端拿到 `wxid_865ki51vfohi22` 无法回答
「这是谁的号、昵称是什么」。

当前唯一的间接途径是 `wechat_contacts` 里 `username == account` 的那一行(微信把
自己也存在本地 `contact` 表,采集端 `collect_contacts()` 不做过滤,顺带传了上去):

```sql
SELECT nick_name, remark, alias FROM wechat_contacts
WHERE account = ? AND username = ?   -- 两个参数传同一个 wxid
```

这不够用:

- **是隐式约定,不是契约**。没有字段标记「这行是账号本人」,靠 `account == username`
  这个巧合。查询方得先知道这条口头知识。
- **不保证存在**。采集端 `db.get_self_info()` 自带兜底:本地查不到自己那行就返回空
  昵称,此时服务端那条记录压根不存在,而不是有个空值。
- **刷新最慢 24 小时**,且源端为空时整批不发(保留服务端已有记录的既定语义)。
- **没有头像**。本地 `contact` 表有 `big_head_url` / `small_head_url`,但联系人实体
  只取了 username/nick_name/remark/alias。
- **没有账号清单**。要回答「现在有哪几个号在采集」只能 `SELECT DISTINCT account
  FROM wechat_messages` 扫大表,而且消息被清掉的号会凭空消失。
- **没有活跃度**。最后同步时间、采集机是哪台,一个都没有,只能靠水位线间接猜。

## 2. 需求:第七张表 + 一个写接口

新增 `wechat_accounts`,一个账号一行,与其余五类实体同样走 upsert。

### 2.1 DDL

追加到 `wechat-core/src/main/resources/db/wechat/wechat_schema.sql`
(建议放在 `wechat_sync_state` 之前,保持业务表在前、状态表在后):

```sql
CREATE TABLE IF NOT EXISTS wechat_accounts (
  account        VARCHAR(64)   NOT NULL COMMENT '微信账号 wxid,与其余各表 account 同值',
  alias          VARCHAR(255)  NOT NULL DEFAULT '' COMMENT '微信号(用户自设,可为空)',
  nick_name      VARCHAR(255)  NOT NULL DEFAULT '' COMMENT '账号昵称',
  remark         VARCHAR(255)  NOT NULL DEFAULT '' COMMENT '账号备注(通常为空)',
  avatar_url     VARCHAR(1024) NOT NULL DEFAULT '' COMMENT '头像地址,按上报值保存,不校验协议与可达性',
  collector_host VARCHAR(255)  NOT NULL DEFAULT '' COMMENT '上报本账号的采集机主机名',
  last_sync_at   BIGINT        NOT NULL DEFAULT 0 COMMENT '采集端本轮同步开始时间(unix 秒)',
  updated_at     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (account)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='采集账号自身信息';
```

`PRIMARY KEY (account)` 直接用业务键,不套 surrogate id —— 一个账号恒定一行,沿用
`wechat_sync_state` 的既有做法,而不是其余五张业务表的 `id` + `UNIQUE KEY` 形式。

### 2.2 字段说明与取舍

| 字段 | 采集端来源(本地 `contact` 表,`username == wxid` 那行) |
|---|---|
| `alias` | `contact.alias`,用户自设的微信号,如 `A18969817099` |
| `nick_name` | `contact.nick_name` |
| `remark` | `contact.remark`,采集机上对自己的备注,实测通常为空 |
| `avatar_url` | `contact.big_head_url`,微信 CDN 公网地址,不经图库 |
| `collector_host` | `socket.gethostname()` |
| `last_sync_at` | 采集端本轮同步开始的 unix 秒 |

已明确**不要**的字段,不要顺手加回来:

- `head_img_md5`:与 `avatar_url` 表达同一件事。
- `small_head_url`:与 `big_head_url` 仅差尺寸后缀(`/0` vs `/132`),存一个够了。
- `account_dir`:带 4 位哈希的本地目录名,`collector_host` 已能定位机器。

`avatar_url` **不做 URL 校验**。它要允许空串表示「没取到头像」,而 `media_url` 的
HTTP(S) 强校验是拒空串的 —— 两者语义不同,不要复用 `media_url` 那条校验分支。

`last_sync_at` 的存在理由:其余实体 upsert 无变化时不写库、`updated_at` 不动,所以
没有它就分不清「账号信息没变」和「采集机挂了三天」。代价是这一行每轮必记
`updated`(见 §3.3),这是有意的。

### 2.3 接口

`POST /api/wechat/accounts`,请求/响应形状与现有五个写接口完全一致:

```json
{
  "account": "wxid_865ki51vfohi22",
  "accounts": [
    {
      "alias": "A18969817099",
      "nick_name": "Winnie9",
      "remark": "",
      "avatar_url": "https://wx.qlogo.cn/mmhead/ver_1/pQOH.../0",
      "collector_host": "WIN-772S7FI9FLV",
      "last_sync_at": 1789377918
    }
  ]
}
```

响应 `{"ok":true,"total":1,"inserted":1,"updated":0,"skipped":0}`。

数组恒定 1 条(一个账号一行),但**不要为此加特殊校验** —— 沿用现有 1~BATCH_LIMIT
的通用规则即可,不值得为它开一条分支。

### 3.2 EntitySpec 新增条目

在 `static { var specs = List.of(...) }` 里补一条(位置随意,`ALL` 是 LinkedHashMap,
按表名查,不按顺序;放在 `sessions` 之后便于阅读):

```java
new EntitySpec("accounts",List.of(),str("alias",255),str("nick_name",255),str("remark",255),
    str("avatar_url",1024),str("collector_host",255),num("last_sync_at",0,Long.MAX_VALUE,false,false)),
```

四个容易踩的点:

1. **`keys` 传 `List.of()`,不要把 `account` 列进去。** `WechatSyncRepository` 里是
   `keys = ["account"] + spec.keys`,再列一遍会让 `WHERE` 变成 `account = ? AND account = ?`,
   并让 `account` 从 `mutableFields()` 里被排除掉。`account` 恒由框架前置。
2. **全部用 `str()`,不要用 `nullable()`。** `str()` 的默认值是 `""`,与 DDL 的
   `NOT NULL DEFAULT ''` 对齐;`nullable()` 的默认值是 `null`,缺字段的行会插 NULL 撞
   `NOT NULL`,变成 500 而不是 400。
3. **`avatar_url` 不会被 URL 校验误伤。** 校验分支是 `f.name().equals("media_url")`,
   按字段名硬编码,新字段名不同自然走不到;空串也能存。这正是 §2.2 要的语义。
4. **`last_sync_at` 用 `num(...)`,第四/五个参数是 `required=false, nullable=false`。**
   与其余数值字段写法一致(参考 `count()` 的展开)。

这条 spec 的 `mutableFields()` 会自动返回全部六个字段(keys 为空 → 一个都不排除),
存在性探测与 `ON DUPLICATE KEY UPDATE` 的字段集随之正确,不需要额外分支。

## 4. 测试

现成的三个测试文件都要动,但**动法不一样**,其中一处不能照抄。

### 4.1 `WechatSyncTest` — 新增独立测试,不要塞进 fixtures

`allSnapshotEntitiesOverwriteDefaultsAndRetainAbsentRecords` 的 `fixtures` 建在
「同一 account 下有多个业务主键行」的前提上(最后断言 `COUNT(*) == 2`)。accounts 的
唯一键就是 `account`,一个 account 恒一行,塞进去断言必挂 —— **不要加那条 fixture**。

改为新增一个测试,覆盖「单行」和「每轮必 updated」这两条 accounts 特有的语义:

```java
@Test void accountRowIsSinglePerAccountAndRefreshesWhenOnlyLastSyncAtChanges() {
    String a=batch("accounts","{\"alias\":\"A1\",\"nick_name\":\"Winnie9\",\"last_sync_at\":100}");
    assertThat(sync.ingest("accounts",a)).isEqualTo(new BatchResult(true,1,1,0,0));
    assertThat(sync.ingest("accounts",a)).isEqualTo(new BatchResult(true,1,0,0,1));
    assertThat(sync.ingest("accounts",
        batch("accounts","{\"alias\":\"A1\",\"nick_name\":\"Winnie9\",\"last_sync_at\":200}")))
        .isEqualTo(new BatchResult(true,1,0,1,0));
    assertThat(jdbc.queryForObject("SELECT COUNT(*) FROM wechat_accounts WHERE account=?",
        Integer.class,account)).isEqualTo(1);
    assertThat(jdbc.queryForObject("SELECT avatar_url FROM wechat_accounts WHERE account=?",
        String.class,account)).isEmpty();
}
```

最后一行是回归点:缺字段走 `str()` 的默认值,落库是 `''` 而不是 NULL(§3.2 第 2 条)。

同时 `@AfterEach` 的清理清单加 `"accounts"`,否则测试数据跨用例残留:

```java
for(String table:List.of("messages","contacts","chatrooms","chatroom_members","sessions","accounts","sync_state"))
```

### 4.2 `WechatControllerTest` — 两处清单各加一个字符串

`routesDelegateToPublicFacade` 与 `oldAndVersionedRoutesAreNotExposed` 里的
`List.of("messages","contacts","chatrooms","chatroom_members","sessions")` 都加 `"accounts"`。
后者顺带覆盖「`/v1/accounts` 不存在」,与既有语义一致。

### 4.3 `WechatIntegrationTest` — 实体循环要单独给一条行形状

实体清单加 `"accounts"` 即可,但 `switch(entity)` **必须补一个 case**:

```java
case "accounts" -> "{\"nick_name\":\"n\",\"last_sync_at\":1}";
```

不能让它落进 `default -> "{\"username\":\"a\"}"` —— accounts 没有 `username` 字段,
校验层会以 `unknown field` 拒掉整批 400。循环里那句重放断言
`wechat.ingest(entity,body).skipped()).isOne()` 对 accounts 同样成立(整行一致 → skipped)。

## 5. 采集端降级行为

采集端已按本文契约实现(改动见采集端仓库同批提交),行为如下,服务端可以据此判断
上线前后的日志表现:

- 每轮同步**开头**调一次 `sync_account()`,数组恒定 1 条。
- **任何失败都不中断本轮**:整个网络路径包在 `try/except Exception` 里,失败只 print 一行
  `账号信息上报失败，跳过本轮: ...`,然后照常同步消息/实体/图片。
- **不影响退出码**。账号信息失败不会让任务以非零码结束,不会触发任务计划程序告警。
- **重试由通用 `_retry` 承担**:5xx 和网络异常退避重试至多 5 次(1s 起,封顶 16s),
  4xx 立即返回。所以服务端未部署时,每轮会先失败 5 次再跳过,约多花 15~30 秒。

  这是已知代价,不在采集端做特判的原因:**服务端对未声明路由返回的是 500,不是 404**
  (实测),而 500 同时也是「数据库写入失败、应退避重试」的正常信号,客户端无法用状态码
  区分两者。与其猜,不如让消息同步照常进行,把失败原因打出来由运维判断。
  `collect_self()` 本身查不到自己那行 contact 时仍会构造一行(空昵称/空头像),
  不会因为「本地没数据」而少发一条。

## 6. 部署顺序

**采集端可以先发,服务端后发,中间没有坏状态。**

| 阶段 | 结果 |
|---|---|
| 只发采集端 | 每轮在消息同步前多打一行 `账号信息上报失败（HTTP 500）`,约多花 15~30s(见 §5),其余完全不受影响 |
| 服务端上线(重启 CRM) | `WechatSchema.initialize` 在启动期间跑 `CREATE TABLE IF NOT EXISTS wechat_accounts`,建表即生效 |
| 建表后的下一轮 | 采集端开始写入,日志变为 `账号信息: Winnie9（A18969817099）` |

两点必须说清楚:

- **建表只在 CRM 启动时发生**,没有在线 DDL,也不需要 Flyway 脚本。现有六张表一个都不动
  —— 初始化只创建缺失的表、**从不升级已有表结构**,所以这次上线对存量数据零风险。
- **反过来不成立**:服务端先上线也不会有人写这张表,必须等采集端下一轮。

## 7. 验收标准

按顺序都能通过即视为完成:

1. 重启 CRM 后 `SHOW TABLES LIKE 'wechat_%'` 返回 7 张,含 `wechat_accounts`。
2. 带有效 JWT `POST /api/wechat/accounts`(body 用 §2.3 的样例)返回
   `200 {"ok":true,"total":1,"inserted":1,"updated":0,"skipped":0}`;原样重放返回
   `skipped:1`;不带 JWT 返回 401;`POST /api/wechat/v1/accounts` 不存在。
3. `SELECT account, alias, nick_name, avatar_url, collector_host, last_sync_at
   FROM wechat_accounts` 能看到真实昵称与微信号;取不到自己那行 contact 的号,
   昵称/头像为空串而不报错。
4. 采集端一轮日志尾部出现 `账号信息: Winnie9（A18969817099）`;`_sync_incremental.log`
   里不再出现 `账号信息上报失败`。
5. 回归:现有五类实体与消息同步的计数与 §5.1 的既有语义不变
   (`verify_backend.py` 的前 3 项检查仍 PASS)。

## 8. 附:采集端实际观测值(取样于 2026-09-14)

本文所有样例取自采集机实测,可直接用于构造请求:

| 字段 | 账号一 | 账号二 |
|---|---|---|
| `account` | `wxid_865ki51vfohi22` | `wxid_axx4tld8xlz612` |
| `alias` | `A18969817099` | `A15381048716` |
| `nick_name` | `Winnie9` | `winnie6` |
| `remark` | (空) | (空) |
| `collector_host` | `WIN-772S7FI9FLV` | `WIN-772S7FI9FLV` |

服务端也不要把空串视为异常。
