# 微信数据同步 · 运维手册

把采集机上的微信数据同步到 aizee 服务端。两个入口:**首次初始化**跑一次,之后
**增量**由定时任务反复跑。

```
[采集机 Windows / Python]  --HTTP-->  [同步服务 primeapi.aizee.cc]  -->  [MySQL]
         |
         +-- 图片 -->  [同一个服务的图库]  --回填 URL-->  同上
```

## 每台机器的前置条件

| 项 | 要求 |
|---|---|
| 微信 | 已登录并在运行。首次要从进程内存提取库密钥和图片 AES key(之后落盘缓存) |
| Python | 3.14,`py` 命令可用;依赖见 `pyproject.toml`,图片转码额外需要 `imageio-ffmpeg` |
| 同步服务 | `https://primeapi.aizee.cc/api/wechat` 可达(或用 `WECHAT_SYNC_BASE` 指向别处) |
| 同步 token | `WECHAT_SYNC_TOKEN`。归档接口和图库在同一服务、共用这一个凭据;缺失或无权会 401/403 |
| 图库 token | `AIZEE_TOKEN`,留空时自动复用 `WECHAT_SYNC_TOKEN` |

同一个微信账号只允许一个采集进程(锁按账号隔离,重复启动会跳过)。`account` 取自
`db.wxid`,服务端按 `account` 天然隔离。换机器前先停掉旧机器的定时任务。

### 一台机器登录多个微信

**默认就会同步本机全部已登录账号**,逐个处理,不需要额外配置:

```bat
sync_wechat.bat
```

- 没同步过的账号会**自动做全量**(服务端水位线为空 → 扫描不收窄 → 等价于首次初始化),
  所以「哪个是首次、哪个是增量」不用你区分,一个 job 全覆盖。
- 每个账号独立上锁、独立记节奏状态(`_sync_state.json` 按账号分区),互不影响。
- 单个账号失败不影响其他账号,末尾汇总失败清单并以非零码退出(便于任务计划程序告警)。
- 图库缓存按图片内容哈希共享:同一张图在多个账号里出现过也只上传一次。
- 每个账号首次提取密钥都需要它的微信客户端登录着。多个微信同时在跑没问题,
  提取逻辑会用各账号自己的库文件校验密钥,错的会被拒掉并继续尝试其它进程。

只同步指定账号(排障或分批上线时用),`--account` 接 wxid 或账号目录名:

```bat
py sync_to_server.py incremental --account wxid_xxxxxxxx
py sync_to_server.py init        --account wxid_xxxxxxxx
```

看本机有哪些账号:

```bash
py -c "from wechatauto.db import list_accounts; [print(a['wxid'], a['account']) for a in list_accounts()]"
```

## 一、首次初始化

```bat
sync_wechat.bat init
```

依次做:四类实体整表覆盖 → 全量消息 + 水位线 → 图片上传 + `media_url` 回填。

参考耗时(8千余条消息 / 8百余会话 / 1148 张图):实体 58s,消息 206s,图片 452s。
数据量大的机器会更久,中断了直接重跑,全部幂等。

想分步跑(便于定位失败)也可以:

```bat
py sync_to_server.py entities
py sync_to_server.py messages
py sync_to_server.py media
```

## 二、增量(定时任务)

**每台机器只需要一个 job**,增量入口自己判断该做什么:

```bat
sync_wechat.bat
```

建议 5~15 分钟一次。参考耗时 66~74s。

在「任务计划程序」里建任务:

- 程序:`D:\github\wechatauto-replica\sync_wechat.bat`
- 起始于:留空即可。`.bat` 内有 `cd /d "%~dp0"` 自定位,已实测从 `C:\` 调用也正常
- 触发器:每 10 分钟重复,持续时间「无限期」
- 保持默认的「只在用户登录时运行」。**不要**选「不管用户是否登录都要运行」——
  那需要存密码,而且采集本身就要求微信在前台登录着,用户必然已登录
- **不要**勾选「如果任务运行时间过长则停止」,耗时较长的全量兜底会被误杀

命令行创建(路径按实际改):

```bat
schtasks /create /tn "WeChatSync" /tr "D:\github\wechatauto-replica\sync_wechat.bat" ^
  /sc minute /mo 10 /f
```

不带 `/ru`,任务就以当前用户身份、仅在登录时运行,不会索要密码。

建完任务后**务必再检查一次任务属性里的「条件」页** —— `schtasks` 建出来的默认值会坑人:

- 取消勾选「**只有在计算机使用交流电源时才启动此任务**」
- 取消勾选「**如果计算机改用电池电源,则停止**」

这两个默认是**开启**的(`DisallowStartIfOnBatteries=true`)。采集机是笔记本时,一拔电源
就静默停止上传,且任务计划程序里看不出异常。用命令行改:

```powershell
$t = Get-ScheduledTask -TaskName "WeChatSync"
$t.Settings.DisallowStartIfOnBatteries = $false
$t.Settings.StopIfGoingOnBatteries = $false
Set-ScheduledTask -TaskName "WeChatSync" -Settings $t.Settings
```

其它默认值(`schtasks` 建的)都是对的,不用动:

| 策略 | 值 | 含义 |
|---|---|---|
| `LogonType` | `InteractiveToken` | 以当前登录用户身份运行,不存密码 |
| `MultipleInstancesPolicy` | `IgnoreNew` | 上一轮没跑完时,新触发直接跳过,不会并发 |
| `ExecutionTimeLimit` | 72 小时 | 够用 |

### 间隔怎么选

一轮的耗时主要花在「消息扫描」上,**按账号线性增长**:单账号增量约 100~150s,
四类实体触发那轮再加约 70s/账号,全量兜底那轮要 300s+/账号。

- 单账号机器:5 分钟没问题。
- 多账号机器:建议 10 分钟。否则一轮超过间隔,每次触发都被 `IgnoreNew` 跳过,
  实际变成背靠背连续跑(不会出错,只是没意义)。

### 一台机器要同时保留多份配置

生产 `.env`(aizee-crm)和联调配置(如 `.env.prime-contact`)都想留着时,不要来回覆盖
`.env`,加一个只负责切换配置的入口,任务指向它:

```bat
REM sync_wechat_prime_contact.bat
setlocal
cd /d "%~dp0"
set WECHAT_SYNC_ENV_FILE=.env.prime-contact
call "%~dp0sync_wechat.bat" %*
exit /b %ERRORLEVEL%
```

### 只跑部分账号

排障或分批上线时,把 `--account` 透传进去即可(入口脚本用 `%*` 转发):

```bat
schtasks /create /tn "WeChatSync" ^
  /tr "D:\github\wechatauto-replica\sync_wechat.bat --account wxid_xxxxxxxx" ^
  /sc minute /mo 10 /f
```


### 每轮实际做什么

| 内容 | 触发条件 | 说明 |
|---|---|---|
| 账号自身信息 | 每轮 | 昵称/微信号/头像 + 采集机名 + `last_sync_at`;一行数据,失败只告警不中断 |
| 消息 | 每轮 | 按服务端水位线只扫 `sort_seq >= watermark` |
| 图片 | 每轮 | 只处理本轮扫到的新图;已传过的命中本地缓存,不重传 |
| 四类实体 | 距上次 ≥ 24h | 整表重新覆盖(`ENTITY_INTERVAL_SEC` 可调) |
| 全量兜底 | 距上次 ≥ 7d | 消息不收窄范围扫一遍(`SWEEP_INTERVAL_SEC` 可调) |

节奏状态存 `_sync_state.json`,所以只要一个 job。

**账号自身信息为什么每轮都发**:`account` 只是各表的关联键,本身不含身份信息,
服务端不单独存一行就只能靠 `wechat_contacts` 里 `username == account` 那条隐式
约定去猜昵称。`last_sync_at` 每轮都变,所以这行必然记 `updated` —— 其余实体无变化
时不写库、`updated_at` 不动,没有它就分不清「账号信息没变」和「采集机挂了三天」。

**全量兜底为什么不能省**:微信换设备登录、漫游同步时会**补写 `sort_seq` 低于当前
水位线的历史消息**,按水位线收窄的扫描看不见它们。兜底那轮绝大部分是幂等
`skipped`,只补真正缺的。

## 三、验证与排障

日志在 `logs\sync_incremental.log`(20MB 自动轮转)。正常一轮的尾部:

```
消息合计: {'total': 942, 'inserted': 0, 'updated': 0, 'skipped': 942}
媒体统计: {'缓存命中': 81, '新上传': 0, ...}
完成，耗时 66.5s
```

`skipped` 占多数是正常的 —— 增量用 `>=` 会重读水位线所在那一秒(每会话约 1 条),
服务端按幂等键判为无变化。这是不丢同秒消息的代价。

看服务端水位线:

```bash
curl -H "Authorization: Bearer <token>" https://primeapi.aizee.cc/api/wechat/watermark/<wxid>
```

| 现象 | 原因 / 处置 |
|---|---|
| `已有同步进程在运行（pid=N），本轮跳过` | 上一轮没跑完。偶发正常;持续出现说明间隔太短 |
| `取不到图片解密密钥` | 微信没运行或没登录，或没在微信里点开过图片。**消息仍能同步，图片这步跳过**（不会中断本轮，也不影响其它账号）。要让图片开始上传，见下方「图片密钥」 |
| `缺少 AIZEE_TOKEN 环境变量` | token 没配。消息和实体不受影响,只是不传图 |
| `同步服务不可用 ... HTTP 401` | 同步 token 缺失/失效,检查 `WECHAT_SYNC_TOKEN` |
| `同步服务不可用 ... HTTP 403 无权执行此操作` | 该 api token 所属账号没有 wechat 同步权限,找 CRM 管理员授权 |
| 整批 400 `unknown field` | 服务端版本比采集端旧。见下方兼容开关 |
| 图片统计里 `格式不支持` | 缺 ffmpeg 且原图是 wxgf。装 `imageio-ffmpeg` 后重跑 |

失败会自动重试:5xx 和网络错误指数退避 5 次;4xx 立即失败(请求本身有问题,重试无意义)。
崩在「消息已落库」与「水位线已提交」之间时,下一轮从旧水位线重放,靠幂等键去重。

## 四、可调环境变量

| 变量 | 默认 | 用途 |
|---|---|---|
| `WECHAT_SYNC_TOKEN` | 无 | 同步服务凭据(**必填**)。归档接口和图库在同一个服务上、共用同一个凭据,所以只配这一个就够 |
| `AIZEE_TOKEN` | 沿用 `WECHAT_SYNC_TOKEN` | 图库 token。留空时自动复用同步 token;只有两个凭据不同的部署才需要单独配 |
| `WECHAT_SYNC_BASE` | `https://primeapi.aizee.cc/api/wechat` | 归档接口地址 |
| `AIZEE_GALLERY_BASE` | `https://primeapi.aizee.cc` | 图库地址(与归档同主机) |
| `ENTITY_INTERVAL_SEC` | `86400` | 四类实体重跑间隔 |
| `SWEEP_INTERVAL_SEC` | `604800` | 全量兜底间隔 |
| `SEND_SENDER_USERNAME` | `0` | 服务端 `wechat_messages` 有 `sender_username` 列时才置 `1`(prime 归档表没有这一列) |
| `WECHAT_SYNC_AUTH` | `direct` | 鉴权方式。`direct`=token 直接当 Bearer 用(prime 这套);`exchange`=老的 aizee-crm 网关,先把 api token 换成短期 JWT |
| `WECHAT_SYNC_HEALTH_PATH` | `/watermark/__health__` | 健康探针路径,用归档接口自身探活(一次请求同时验证可达+鉴权+归档模块+数据库) |
| `WECHAT_SYNC_ENV_FILE` | 同目录 `.env` | 换读另一份配置文件,不必覆盖 `.env`。真实环境变量仍优先 |
| `IMAGE_KEY_WAIT_SEC` | `120` | 抓图片 AES 密钥时等待「用户点开一张图」的秒数。**定时任务里置 `0`**,否则每轮白等两分钟 |

### 图片密钥怎么才能拿到

图片 AES 密钥有两种来源,优先级从高到低:

1. **cfgDword 离线派生**(`MD5(str(cfgDword)+wxid)[:16]`)。确定性、不需要人看图,但
   `CFG_OFFSET` 等锚点是**版本敏感**的。实测微信 `4.1.13.65` 下 `*(v18+0x68)` 取到 0,
   派生链断掉,只能走第 2 条。换微信版本后如果图片突然全传不了,先怀疑这里。
2. **进程内存扫描**。密钥只在微信**点开图片查看之后**才驻留内存约 5 分钟。所以首次
   启用图片要这么做:保持微信登录 → 设 `IMAGE_KEY_WAIT_SEC=120` → 跑一次
   `sync_wechat.bat media`(或 `py sync_to_server.py media --account <wxid>`),
   按提示在微信里点开任意一张图 → 抓到后持久化到
   `%TEMP%\wechatauto_db\<账号>\image_keys.json`。

持久化之后,定时任务里的图片上传就完全不需要人工了(命中缓存直接解密)。
反过来,`image_keys.json` 是**按机器+按账号**的:新机器、或者换了微信账号,都要重来一次。


## 五、运行时文件(都已 gitignore)

| 文件 | 用途 | 可否删除 |
|---|---|---|
| `_media_url_cache.json` | md5 → 图库 URL,避免重复上传;多账号共享 | 可删,但下次会重新逐张查图库(慢,不会重复传) |
| `_sync_state.json` | 按账号分区的节奏时间戳 + 未确认的回填队列 | 可删,删后每个账号会各触发一次实体覆盖和全量兜底 |
| `_sync_<账号>.lock` | 单进程锁,内含 PID,每账号一个 | 进程死了会自动接管;不要手动删活进程的锁 |
| `token.txt` | （历史遗留）早期图库 token 兜底文件,当前代码不再读取 | 不需要 |

## 六、已知边界

- **只同步图片**。图库仅接受 `png/jpg/jpeg/webp/gif`,所以语音(`.silk`)、视频
  (`.mp4`)、文件和链接卡片都传不上去,`media_url` 保持为空。
- **画质取决于本地磁盘**。微信只在图片被点开看过时才下载原图,否则本地仅有缩略图。
  有原图的传原图(wxgf 经 ffmpeg 转 jpg),否则传缩略图。
- **消息只追加**。写入后只有 `media_url` 和 `sender_name` 能通过接口更新（前者等媒体回填，
  后者等发送者名字解析改进），其余字段只能直连 SQL。所以发送者名字算错时，重跑一次
  `sweep` 就能回填，不必清库重传。
- **四类实体不反映删除**。联系人删除、成员退群、会话消失后,服务端保留已见记录,
  这个集合不等于源端当前集合。
- **账号头像是微信 CDN 地址**,不经图库,按上报值原样保存,不校验可达性;微信换头像
  后旧 URL 可能失效。取不到自己那行 contact 时仍会上报一行,只是昵称/头像为空。
- **`wechat_sessions.summary` 含消息正文片段**,可能带敏感内容(我们在实测数据里
  见过形似 API key 的字符串)。往共享库灌之前请确认合规边界。
- **访问控制**。归档接口本身**要求鉴权**(prime 这套的 `/api/wechat/**` 需要
  `SUPER_ADMIN` 角色,凭据就是 `WECHAT_SYNC_TOKEN`),但 `account` 只是数据来源
  标识、不是凭据 —— 拿到同一个 token 就能操作全部来源账号。现在通过公网域名
  `primeapi.aizee.cc` 暴露,网关层仍建议加来源 IP 白名单,并全程走 HTTPS。
